# Concrete JUCE iOS project comparison

Read-only research, 9 September 2026. Three released audio projects and one small JUCE diagnostic application were traced from their iOS build definitions through their standalone initialization to the actual native backend they include. Only public source files and indexes were downloaded; no repository was cloned, no application was built or installed, and no device settings or project code were changed.

**Main result:** these examples do not reveal a special USB-safe AVAudioSession configuration that SmartGridOne is missing. All three applications' inspected standalone paths use RemoteIO, allow mixing, retain active sample-rate/buffer probing, and retain JUCE's historical one-extra-frame buffer-duration request. SonoBus explicitly starts from 48 kHz/256 frames. BYOD and CHOW Tape leave rate/buffer preferences to saved settings and JUCE defaults. Those are useful comparisons of source configuration, not demonstrations of reliability on the MAYA44 USB+ and iPadOS 26.6.1.

Version provenance was checked in [SonoBus's module header](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/modules/juce_core/system/juce_StandardHeader.h#L30-L32), [its subrepo metadata](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/.gitrepo#L6-L10), [BYOD's pinned module header](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_core/system/juce_StandardHeader.h#L30-L32), and [CHOW Tape's pinned module header](https://github.com/lv2-porting-project/JUCE/blob/ebbe26fd877ac7248c9bb800b56a4786bf538cdb/modules/juce_core/system/juce_StandardHeader.h#L30-L32). The application SHAs were resolved from their public main/master branches during this research. Their dates matter: these source snapshots do not establish what any presently installed App Store binary contains.

**Our actual baseline.** The relevant local checkout is `/Users/joyo/.codex/worktrees/e18e/theallelectricsmartgrid`, not the unrelated working changes on main. [OpenAudioDevice](../historical-context/JUCE/SmartGridOne/Source/MainComponent.cpp#L254) explicitly requests 48 kHz/512 frames, zero physical inputs and seven outputs, supplies no saved device XML, and disables fallback on initialization failure. It clears the input mask and closes a device whose accepted rate is unsuitable. The observed MAYA run had zero inputs and four outputs according to the supplied experiment packet. [SampleTimer](../historical-context/private/src/SampleTimer.hpp#L7) defines the required 48 kHz rate.

The shared native file at `/Users/joyo/JUCE/modules/juce_audio_devices/native/juce_Audio_ios.cpp` is byte-identical to [upstream 8.0.2](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_devices/native/juce_Audio_ios.cpp). The app's [copy-generation script](../historical-context/JUCE/SmartGridOne/scripts/prepare_ios_audio_module.py#L14) makes precisely two native replacements: remove the extra frame from the requested duration, and change the physical-device default from 256 to 512. [The iOS exporter](../historical-context/JUCE/SmartGridOne/SmartGridOne.jucer#L70) persists the prebuild and header precedence. The checked definitions contain no override disabling mixing, no explicit sample-rate list, and no app call enabling measurement mode.

Consequently, these are inherited JUCE behaviors, rather than explicit SmartGrid app choices:

- Device construction first selects PlayAndRecord and activates the session to enumerate hardware, then deactivates it—even for an eventual output-only device. Opening activates the session, selects Playback for a zero-input request, and applies the target rate/buffer. [Native constructor/open](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L261-L284), [open](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L463-L499).
- MixWithOthers is added unless a compile-time option disables it. The inspected path does not select an AVAudioSession mode. A separate preprocessing API selects Default or Measurement only if called. Describing SmartGrid as explicitly configured for Measurement would be wrong. [Category options](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L289-L309), [mode setter](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L557-L569).
- The audio component is RemoteIO. Capability enumeration actively requests trial rates and 64/4096-frame durations. Native route handling can schedule hardware refresh and restart. Neither of our two patches changes those mechanisms. These backend facts are the same mechanisms observed in the external sources below.

**SonoBus: an explicit 48 kHz preference with a small native fork.**

Its [custom standalone application's createWindow](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/Source/SonoStandaloneFilterApp.cpp#L182-L197) sets 48 kHz and, on iOS, 256 frames. These are preferences: its [holder reloads saved device settings](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/Source/SonoStandaloneFilterWindow.h#L380-L455), and a user option can remove the saved rate and replace the preferred rate with zero. It initializes from the plugin's main bus counts; [the plugin defines stereo main input/output](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/Source/SonobusPluginProcessor.cpp#L547-L554), while the standalone holder disables non-main buses. Thus fresh standalone initialization normally opens two inputs/two outputs when recording permission is granted, unlike our zero-input/four-active-output test.

The [iOS Projucer settings](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/mobile/SonoBusMobile.jucer#L409-L443) explicitly enable microphone permission and background audio, target iOS 11, and select `deps/juce/modules`. The committed Xcode project also points to that directory; the separate top-level JUCE directory is not this build's backend. A misleading-looking rate-list definition begins with `NOTUSED_`; it does **not** define the actual JUCE explicit-rate macro.

Its [native backend](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L277-L400) retains mixing, the +1-frame duration formula, and rate/buffer probing. Unlike stock JUCE 8.0.2, it leaves Bluetooth HFP input disabled by default; A2DP/AirPlay remain permitted for PlayAndRecord. Its audio-unit creation selects [RemoteIO](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L1007-L1025), not VoiceProcessingIO. No call selecting Measurement was found in the inspected initialization, options, processor, or platform utility code.

The native fork additionally classifies USB, line-out and headphones as external listening routes. That classification drives [feedback muting in the holder](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/Source/SonoStandaloneFilterWindow.h#L747-L765). Its [route handler](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L806-L848) retains JUCE's category/configuration-change exclusions and schedules refresh for the other route reasons; [restart](https://github.com/sonosaurus/sonobus/blob/35f1062dab196b9838a4bb529c4bf6592b7f5987/deps/juce/modules/juce_audio_devices/native/juce_Audio_ios.cpp#L1175-L1220) reapplies target settings and recreates the running audio unit.

These changes concern route selection and preventing feedback, not a demonstrated correction to USB clock drift or periodic analog holes. SonoBus supplies a concrete counterexample to the idea that 48 kHz itself is an unusual app choice, but it is not a measured MAYA success case here.

**BYOD: standard stereo effect wrapper, with almost our same native code.**

[Its build](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/CMakeLists.txt#L34-L38) selects Standalone and AUv3 on iOS, [requests microphone permission](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/CMakeLists.txt#L86-L113), and [archives the standalone target for iOS 11.4](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/scripts/ios_build.sh#L20-L32). The inspected build definitions do not replace JUCE's standalone application or set native audio macros.

[The stock standalone app passes no preferred setup](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_audio_plugin_client/juce_audio_plugin_client_Standalone.cpp#L81-L101). Its [holder supplies saved audio XML, channel counts and fallback permission](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_audio_plugin_client/Standalone/juce_StandaloneFilterWindow.h#L318-L348). [BYOD inherits stereo buses](https://github.com/Chowdhury-DSP/chowdsp_utils/blob/34db5bd24adace1771c0e734ced13dc5624295ff/modules/plugin/chowdsp_plugin_base/PluginBase/chowdsp_PluginBase.h#L163-L169) and [prepares DSP using the delivered rate/block size](https://github.com/Chowdhury-DSP/BYOD/blob/1cf22b6ac802b9dc33cfc9f8dd6af5b3c3e40bc9/src/BYOD.cpp#L54-L63). It does not enforce SmartGrid's fixed 48 kHz contract.

Its inherited physical-device buffer default is 256. An unspecified rate is selected using JUCE's [requested/current/supported-rate logic](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_audio_devices/audio_io/juce_AudioDeviceManager.cpp#L829-L867), not an explicit BYOD 44.1 kHz preference. Likewise the wrapper's provisional processor initialization numbers are not hardware requests. [The input mute](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_audio_plugin_client/Standalone/juce_StandaloneFilterWindow.h#L624-L638) substitutes zero samples; it does not close physical inputs. With recording permission granted, the native category is therefore PlayAndRecord even while input is muted.

Byte comparison of [BYOD's pinned native file](https://github.com/juce-framework/JUCE/blob/a8ae6edda6d3be78a139ec5e429dc57ef047e82a/modules/juce_audio_devices/native/juce_Audio_ios.cpp) against our unmodified JUCE 8.0.2 found only the licence header and removal of pre-iOS-10 compatibility branches for A2DP/URL opening. On our current iPad these do not change audio behavior. The rate/buffer probing, mixable session, optional mode setter, RemoteIO creation and route/restart logic are otherwise the same. Our two app-local patches are the substantive differences in that native file. This is stronger evidence than inferring behavior from the version numbers alone.

**CHOW Tape: another real standalone app, with older JUCE defaults.**

[The iOS CMake branch](https://github.com/jatinchowdhury18/AnalogTapeModel/blob/604372e4ffd9690c3e283362e4598cb43edbb475/Plugin/CMakeLists.txt#L24-L67) builds Standalone/AUv3 with microphone permission, and the [archive script](https://github.com/jatinchowdhury18/AnalogTapeModel/blob/604372e4ffd9690c3e283362e4598cb43edbb475/Scripts/ios_builds.sh#L22-L32) targets iOS 11.4. Its [submodule configuration](https://github.com/jatinchowdhury18/AnalogTapeModel/blob/604372e4ffd9690c3e283362e4598cb43edbb475/.gitmodules) points to the LV2 JUCE fork, but that fork's native iOS file at this pin is byte-identical to upstream 6.1.6.

Its [standalone app also passes no preferred setup](https://github.com/lv2-porting-project/JUCE/blob/ebbe26fd877ac7248c9bb800b56a4786bf538cdb/modules/juce_audio_plugin_client/Standalone/juce_StandaloneFilterApp.cpp#L74-L93); the [holder restores saved settings and opens the main channels](https://github.com/lv2-porting-project/JUCE/blob/ebbe26fd877ac7248c9bb800b56a4786bf538cdb/modules/juce_audio_plugin_client/Standalone/juce_StandaloneFilterWindow.h#L315-L345). Its [base processor defaults to stereo in/out](https://github.com/Chowdhury-DSP/chowdsp_utils/blob/39851f124e26c1d5ef92a298a5e0973650075b57/modules/plugin/chowdsp_plugin_base/PluginBase/chowdsp_PluginBase.h#L116-L121), and [DSP preparation follows the delivered format](https://github.com/jatinchowdhury18/AnalogTapeModel/blob/604372e4ffd9690c3e283362e4598cb43edbb475/Plugin/Source/PluginProcessor.cpp#L93-L115).

The [6.1.6 native source](https://github.com/lv2-porting-project/JUCE/blob/ebbe26fd877ac7248c9bb800b56a4786bf538cdb/modules/juce_audio_devices/native/juce_ios_Audio.cpp) supplies the 256-frame physical default, +1-frame duration request, active rate/buffer probing, mixable PlayAndRecord with inputs, and RemoteIO. The inspected standalone path does not select Measurement or VoiceProcessingIO. Compared with our backend, its category options lack the explicit AllowAirPlay option; this is not evidence of a USB playback improvement. Its route callback still schedules asynchronous hardware refresh/restart. Its muted-input behavior is software muting, as in BYOD. These two ChowDSP applications share framework conventions, so they are not fully independent evidence for a configuration rule.

**Small diagnostic comparison.** [AudioPerformanceTest's constructor](https://github.com/juce-framework/JUCE/blob/8.0.2/extras/AudioPerformanceTest/Source/MainComponent.h#L46-L54) requests zero inputs/two outputs through AudioAppComponent; [its project has an iOS exporter](https://github.com/juce-framework/JUCE/blob/8.0.2/extras/AudioPerformanceTest/AudioPerformanceTest.jucer#L34-L52). [AudioAppComponent](https://github.com/juce-framework/JUCE/blob/8.0.2/modules/juce_audio_utils/gui/juce_AudioAppComponent.cpp#L59-L91) initializes the device with no format preferences and attaches AudioSourcePlayer. This inherits Playback after the initial PlayAndRecord enumeration, mixing, 256 frames and normal JUCE probing/restarts. It is an output-only structural example, not a USB-specific success report or a pure sine source. No independently verified minimal MAYA-specific diagnostic repository was found in this search.

**What matters for this investigation.**

1. SmartGrid's 48 kHz preference, output-only session, RemoteIO, or mixability cannot be identified as wrong merely by contrasting it with “other JUCE apps.” There are concrete examples of the same choices, and several shared native mechanisms. None supplies a controlled MAYA/iPadOS 26.6.1 result.
2. The specific differences worth retaining in the hypothesis list are: 512 versus inherited 256-frame preferences; actual input-channel opening versus software muting; fixed accepted sample-rate requirements versus adapting DSP; initial native enumeration and subsequent format-setting order; and the native JUCE revision/patch set. Existing recordings already cover several of the first three variations, so source comparison alone is not a reason to repeat them.
3. These inspected apps do **not** demonstrate that skipping capability probing is an established working solution. SonoBus even carries a disabled explicit-rate-list definition. Suppressing probing would be a distinct experiment, and any such experiment must retain reliable actual-rate/buffer verification.
4. There is no source evidence here that changing to VoiceProcessingIO or Measurement is required for USB stability. None of the inspected standalone initialization paths makes either choice. A default-mode claim concerns expected process initialization, not a measurement of the currently running AVAudioSession.
5. An AUv3 run inside AUM/Drambo or another host does not exercise the plugin's standalone device manager. The host selects the session/device configuration. A future public-app comparison would need the actual standalone binary version, session state, accepted format and callback sizes recorded before it could distinguish configurations.
6. This source survey cannot explain the initiating cause of the late tone-only periodic holes. It establishes neither the semantics of `ioDriftNS` nor why Drambo remained clean. The observed absence of long callback gaps, xr increments and USB restarts during that symptom remains stronger evidence about that run than any assumption based on an app's popularity.

The corresponding downloaded source files, pinned tree/commit metadata, and comparison inputs are retained beside this report with `sonobus-`, `byod-`, `chowtape-`, and `juce8-` prefixes. Every claim above refers to inspected source/build paths; none is a claim that these public snapshots were executed in our hardware setup.
